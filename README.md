# Podcast Listening Analytics: dbt Project

An analytics-ready data model built over raw podcast interaction logs, supporting analysis of episode performance, listen-through behaviour, and user engagement.

Built with dbt Core 1.10.15 on DuckDB.

This README is longer than a project of this size usually warrants, deliberately. The modelling here is small; the decisions behind it are the point, so they are written down rather than left implicit.

**Listen-through rate**, used throughout, means the duration a listener actually consumed divided by the episode's own length, capped at 1.0. Section 4 explains why the capping is necessary. It is abbreviated LTR in some filenames.

## 1. The scenario

A podcast streaming service records raw interaction events as users listen: plays, pauses, seeks, completions and downloads. Each event carries a user, an episode, a timestamp, and for playback events a duration. Alongside these sit two reference files describing users and episodes.

The raw log is not usable for analysis as it stands. Some events are missing identifiers, some timestamps are unparseable, and a large share of recorded durations exceed the length of the episode being listened to. The task this project sets itself is to turn that log into a clean, tested, analytics-ready model that supports three kinds of question:

- Which episodes and podcasts perform best?
- How completely do people listen, and does that vary by country, podcast or episode length?
- How engaged are users, and how concentrated is their listening?

The data is synthetic and generated by `scripts/generate_seed_data.py`, which is committed alongside the project. Most of its flaws are deliberately injected at known rates so the validation and transformation layers have something real to handle. The generator is seeded, so the dataset reproduces exactly.

**Dataset shape:** 400 users, 200 episodes across 30 podcasts, and 40,000 interaction events spanning January 2025 to February 2026.

## 2. Setup and run instructions

```bash
# From the project root
python3.11 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cd podcast_analytics
export DBT_PROFILES_DIR=$(pwd)     # Windows PowerShell: $env:DBT_PROFILES_DIR = (Get-Location).Path

dbt deps
dbt build                          # runs seeds, models and tests together
dbt docs generate && dbt docs serve
```

**Running the analyses.** dbt compiles the files in `analyses/` but does not execute them. To run them all and print the results:

```bash
dbt compile
python scripts/run_analyses.py
```

**Regenerating the data.** The seed CSVs are committed, so this is not needed to run the project. To produce a fresh dataset, adjust the constants at the top of the generator and run:

```bash
python scripts/generate_seed_data.py seeds
```

Every figure quoted in this README is derived from the committed seeds. Changing the generator's `SEED` value or its parameters will change them.

**Python version.** dbt Core 1.10 is not compatible with Python 3.13 or later (a `mashumaro` serialisation error prevents dbt from starting at all). This project was built on Python 3.11.9.

## 3. Assumptions

Nothing in the raw data specifies who consumes this model or how, so the following assumptions shaped the design. Each is a judgement call rather than a given.

| | |
|---|---|
| **Who** | Technical, squad-based analysts and analytics engineers, comfortable writing SQL and joining tables. |
| **What** | An analytics-ready model over podcast interaction events, supporting completion analysis, listen-through rate, and user engagement or cohort analysis. |
| **When** | Daily batch refresh, running overnight so that squads have current figures at the start of the working day. The project itself runs against a static seed. |
| **Where** | dbt on the warehouse, with a BI layer as a plausible downstream consumer but out of scope here. |
| **Why** | Understanding content performance and user engagement, to inform content investment and product decisions. |
| **How** | Consumed directly via SQL against the marts, rather than through a dashboard. |

The "who" assumption is the most consequential one. Because the audience is technical, I have not flattened everything into wide, join-free tables. A conventional star schema (fact plus slim dimensions) is appropriate for an audience comfortable with joins, and communicates grain more clearly than heavy denormalisation would. That said, the marts are still intended to be readable without a data dictionary open alongside them.

### Source data as seeds

The three CSVs are loaded via `dbt seed` and referenced with `ref()`. In production, event logs of this kind would arrive as ingested warehouse tables and be declared in a `sources.yml`, referenced with `source()` instead. Seeds are intended for small, static reference data, not a growing event stream. The staging models themselves would be unchanged by that switch.

## 4. Data quality findings

Three terms are used throughout this section and defined here, since the reconciliation table depends on them. A **staged** event is any raw row that survived deduplication. A **valid** event is a staged row that passed all six validity checks. A **rejected** event is a staged row that failed at least one, and is quarantined rather than dropped. Section 5 covers where each lives in the model layer.

### Reconciliation

Every raw row is accounted for. `analyses/01_data_quality_summary.sql` reports the full summary:

| Stage | Rows |
|---|---|
| Raw events | 40,000 |
| Removed as duplicates | 2 |
| Staged events | 39,998 |
| Valid events | 38,624 |
| Rejected events | 1,374 |

### Rejected events

Of 39,998 staged events, **1,374 (3.4%) failed at least one validity check** and were quarantined rather than silently dropped.

| Check | Rows |
|---|---|
| Missing `user_id` | 469 |
| Missing `episode_id` | 358 |
| Missing `event_type` | 202 |
| Missing `timestamp` | 218 |
| Malformed `timestamp` | 143 |
| Missing `duration` on a play/complete event | 118 |

These sum to 1,508 rather than 1,374 because **134 rows fail two checks simultaneously**. This is why rejection reasons are stored as independent boolean flags rather than a single reason label (see [Modelling approach](#5-modelling-approach)).

3.4% of staged events are excluded from the analytical models. Whether that exclusion is *biased* is a separate question: it would depend on whether rejected rows cluster by country, event type, date or episode. That is checkable against `rejected_event_logs`, but it is not analysed here, so the rate alone should not be read as reassurance.

### Duplicate events

Two raw rows are identical in every field: same user, same episode, same event type, same timestamp to the second, and no duration. Because `event_id` is a hash of the row's content, they receive the same identifier and are genuinely indistinguishable rather than merely similar. `stg_event_logs` keeps one of each pair.

There is a pattern worth noting in which rows collided. Both duplicates carried a blank `user_id` **and** a blank `timestamp`, and the rejection counts fall by exactly two on each of those checks after deduplication. That is not coincidence. Blanking a field removes one of the values that distinguishes one record from another, so rows with multiple nulls are far more likely to collide on a content-derived hash than clean rows are. Deduplication therefore bites hardest on precisely the rows already being quarantined, which is an interaction between two independent design decisions rather than a property of either alone.

The underlying issue is that identity is being derived from content because the source emits no event identifier of its own. In production the right fix is upstream: have the source system emit an event ID, so two genuinely distinct events that happen to look identical remain distinguishable.

### Malformed timestamps

143 rows contain the literal string `malformed-date`. This is why `timestamp` loads as a string rather than a timestamp type, and why `stg_event_logs` uses `try_cast` rather than `cast` on that column: a plain cast fails the entire model on the first unparseable value rather than isolating the affected rows.

The check for malformed timestamps is written generically (present but unparseable) rather than matching the literal string, so it would also catch other malformed values not present in the current data.

`signup_date` and `release_date` use a plain `cast`, as neither has shown a malformed value. Applying `try_cast` everywhere would be defensive without cause, and would mask genuine upstream problems by silently nulling them.

### Listen durations exceeding episode length

**47% of play/complete events (8,694 of 18,454) have a recorded `duration` greater than the episode's own length**, by up to 15.4 times. Taken raw, the average listen-through rate across the dataset is around 4.1, which is not a plausible figure to report.

The cause cannot be determined from the data alone. Plausible real-world explanations include:

- **Dynamic ad insertion**, where the served audio is longer than the content duration held in metadata
- **Cumulative duration counting**, where rewinding and re-listening within a single logged event inflates the total
- **Heartbeat-based tracking**, where a dropped connection or retry double-counts pings
- **Stale episode metadata**, if an episode was re-edited after its duration was first recorded

**Treatment:** the fact table carries three fields rather than one.

- `duration_raw_seconds`: the original value, retained for audit only, never used in a calculation
- `duration_capped_seconds`: capped at the episode's length via `least()`, the only field that feeds any rate or aggregate
- `duration_exceeds_episode_length`: a boolean flag so affected rows remain identifiable

This keeps reported metrics plausible without discarding 47% of the listening data or hiding the anomaly. The rule is applied consistently: **every duration-based metric in the project uses the capped value**, not only listen-through rate. One consequence worth stating explicitly is that `total_capped_listen_seconds` in `mart_user_engagement` will therefore read lower than a naive sum of raw durations. That is the correct outcome given the reasoning above, not an oversight.

It is worth being clear that capping is the right treatment only under some of the explanations above. If the cause is ad insertion or passive playback, the raw value reflects genuine listening measured against the wrong denominator, and capping is appropriate. If the cause were an application bug double-counting playback, the value would simply be wrong, and excluding the affected rows would be more honest than capping them. Establishing which applies is the first thing I would want to confirm with whoever owns the event tracking.

### Events preceding episode release

**8,045 valid events (20.8%) are dated before their episode's `release_date`.** Unlike the duration anomaly, this one is not merely implausible, it is impossible: nobody can listen to an episode that has not been published.

This one is not a deliberately injected flaw. The generator constrains each event to fall after its user's signup date, but never constrains it against the episode's release date, and it draws release dates from a window that overlaps the event period. The overlap is what produces the 20.8%. I found it while validating the structural claims in this section, not while designing the dataset, and I have left it in rather than regenerating: it is a realistic class of error, and the modelling question it raises is a real one. Being straight about its origin seems better than presenting it as something I planted.

The rows are flagged on the fact table (`is_before_episode_release`) rather than quarantined. The reasoning differs from the rejection cases. A row with a missing `user_id` cannot be attributed to anyone and is unusable; a row dated before release is fully usable, and the discrepancy is in the relationship between two dates rather than in the event itself. Rejecting a fifth of the dataset over that would be a far larger intervention than the problem warrants.

Against real data the first question would be which date is wrong. A `release_date` recorded as the original commission date, a re-publication that reset the field, or a timezone boundary in the event pipeline would each produce this pattern and each imply a different fix. The count is reported in `01_data_quality_summary` so the scale stays visible.

### No session structure

Events are independent records with no session identifier and no terminal event. There is no `stop` or `end` event type, and `pause` cannot reliably be treated as the end of a listen (a user may pause and resume). Completions regularly appear for a user and episode with no preceding `play`, and some user-episode pairs have more than one `complete`.

Sessions therefore cannot be reconstructed from this data. Anything requiring a genuine start-and-stop boundary, true total listening time, within-episode drop-off, whether seeking predicts abandonment, is not derivable here. Achieving it would require either a client-supplied `session_id` or a defined event lifecycle with an unambiguous terminal event. This limitation recurs throughout the sections below.

### Structural observations

- Identifiers are opaque (`usr_9cc5e23781`, `epi_563cdee4fb`, `pod_76434cf79d`) rather than sequential. Sequential identifiers leak information such as approximate volume and creation order, and are brittle if data is ever merged across systems.
- `episode_id` carries no ordering, so it cannot be used as a sequencing proxy. Release order must come from `release_date`.
- Catalogue sizes vary considerably, from 3 to 13 episodes per podcast. This matters for any podcast-level ranking, as set out under `04_best_performing_podcasts_alltime` below.
- All non-null `user_id` and `episode_id` values resolve to their dimensions. There are no negative or zero durations, and no events dated before a user's signup.

## 5. Modelling approach

```
seeds  ->  staging  ->  dimensions / fact  ->  marts
                                          \->  intermediate  ->  analyses
```

The directories are `staging/`, `marts/` and `intermediate/`; the dimensions, the fact table and the mart all share `marts/`. `rejected_event_logs` sits there too despite being a quarantine table rather than something a consumer queries, which is a naming compromise rather than a considered choice.

`int_user_daily_activity` is a leaf rather than a step on the path to the marts: `mart_user_engagement` aggregates the fact table directly. The intermediate model exists because daily grain is genuinely useful on its own, not because the mart needs it.

| Model | Grain | Purpose |
|---|---|---|
| `stg_users` | One row per user | Type casting only |
| `stg_episodes` | One row per episode | Type casting only |
| `stg_event_logs` | One row per raw event | All cleaning, casting, deduplication and validity flagging |
| `dim_users` | One row per user | Adds `signup_year`, `signup_month` |
| `dim_episodes` | One row per episode | Adds duration in minutes, release year/month, length bucket |
| `fct_listening_events` | One row per **valid** event | The central fact table |
| `rejected_event_logs` | One row per **rejected** event | Quarantine, auditable |
| `int_user_daily_activity` | One row per user per day with a listen | Daily aggregation |
| `mart_user_engagement` | One row per user | User-level aggregation |

### Compute once, reference everywhere

The organising principle throughout is that any definition or derived value is computed in exactly one place and referenced everywhere downstream. Three examples:

- **The surrogate key** (`event_id`) is generated once in `stg_event_logs`. Both the fact table and the quarantine table inherit it. Computing it independently in each would risk two different hashes for the same underlying row.
- **`duration_capped_seconds`** is derived once in the fact table. No downstream model recomputes the capping logic, and none uses the raw value.
- **`is_listen_event`** encodes the definition of "listened" as a physical column rather than a convention. Every model needing it filters on the column instead of repeating `event_type in ('play', 'complete')`, so the definition cannot silently diverge between two queries.
- **`listen_through_rate`** is derived once on the fact table, which also carries `episode_duration_seconds` so consumers do not need to re-join `dim_episodes` to get the denominator. 

This is also why `stg_event_logs` performs all validity checking. Both `fct_listening_events` and `rejected_event_logs` are pure filters on its output (`where not is_rejected` and `where is_rejected` respectively), holding no rejection logic of their own.

### Quarantine rather than discard

Invalid events could simply be filtered out. Instead they are routed to `rejected_event_logs`, where they remain countable, testable and auditable. Silent filtering makes data loss invisible; quarantining makes it a measurable quantity.

Rejection reasons are stored in two complementary forms:

- **Six boolean flags** (`is_missing_user_id`, `is_malformed_timestamp`, and so on). Because 134 rows fail more than one check, a single reason column would have required either an arbitrary priority rule or string parsing. Independent flags avoid both, and allow clean aggregation: `count(*) where is_malformed_timestamp` is correct regardless of what else that row failed.
- **A derived `rejection_reason_summary`**, a readable comma-separated string. This is computed *from* the flags, never entered independently, so the two cannot disagree. The flags serve querying and testing; the summary serves anyone reading the table directly.

`rejection_reason_count` records how many checks failed, preserving the fact that a row had multiple problems.

### Surrogate key and deduplication

`event_logs` has no natural key, unlike `users` and `episodes`. `event_id` is generated with `dbt_utils.generate_surrogate_key()` hashed across the raw source columns.

It is hashed on the **raw, unparsed** values, before `try_cast` is applied. A row's identity should not depend on whether it happened to parse successfully. Two rows with identical raw content receive the same `event_id` regardless of what downstream cleaning does to them.

That property has a direct consequence: two raw rows identical in every field are, by this definition, the same event. `stg_event_logs` keeps one of each pair via a `qualify` clause. This is the only defensible treatment given the data available, since nothing distinguishes the rows, but it does mean the model cannot represent two genuinely distinct events that happen to share every attribute. The fix belongs upstream, in a source system that emits its own event identifier rather than identity being inferred from content.

Elsewhere, no surrogate keys are manufactured. `dim_users` and `dim_episodes` carry their natural keys through unchanged, and aggregated models are keyed by whatever they group on (`user_id` for `mart_user_engagement`, `user_id` plus `event_date` for `int_user_daily_activity`).

### Defining "listened"

"Listened to three or more different episodes in one day" requires a definition of listening that the raw data does not supply. Three candidate definitions were tested, and the choice materially changes the answer:

| Definition | Result |
|---|---|
| Any event type | 173 users |
| `play` or `complete` | **72 users** |
| `play` only | 25 users |

**`play` or `complete` was chosen.** Each is independently sufficient evidence that a listen occurred: a `play` asserts the user started the episode, a `complete` asserts the system recorded it as finished. Either alone supports the claim.

`pause` and `seek` are different in kind. They describe how an already-occurring listen unfolded rather than asserting that one happened. In a system with linked sessions this distinction would be immaterial, as a `pause` would always follow a `play` within the same session. Without that linkage, a lone `pause` or `seek` for a user and episode cannot be attributed to a genuine listen, and is closer to noise than signal.

`download` is excluded for a different reason again. It records an intention to consume later rather than consumption itself, and carries no duration. Treating a download as a listen would inflate engagement with events that may never correspond to anything being heard.

This is a reasonable working definition given the data available. In a real business setting I would confirm the intended definition with product owners and whoever maintains the event tracking schema, since "listened" is likely to have an established meaning elsewhere in the business that this analysis should align with rather than redefine.

### Episode length buckets

`episode_length_bucket` classifies episodes as short (under 20 minutes), medium (20 to 45 minutes) or long (45 minutes and over). These thresholds are provisional, chosen by inspecting the duration distribution (mean around 45 minutes, range 6 to 87 minutes), not derived from any business definition. They should be confirmed with a business stakeholder before being treated as canonical, as different cutoffs would move episodes between buckets and change the reported listen-through rates in `07_avg_ltr_by_episode_length_bucket`.

The current split gives 38 short, 66 medium and 96 long episodes, so all three buckets carry enough data to compare.

### Materialisation

Every model is a view. The seed is fully reloaded on each run, so there is no incremental state to preserve. In production the fact table is the one that would change first, becoming incremental against an append-only stream; the two aggregates would likely become tables once they are queried more often than they are rebuilt. `data_refreshed_on` is a casualty of this choice worth naming: on a view it evaluates at query time rather than build time, so it currently reports when you asked rather than when the data landed. It would become meaningful the moment these models were materialised as tables.

### Scope

Three use cases anchored the design: top episodes by completion, average listen-through rate, and retention or engagement by cohort. Any candidate metric was tested against whether it served one of those, which kept the model focused rather than speculative.

Several extra analyses were brainstormed and added whilst some were deliberately cut. Where something was investigated and set aside, the reasoning is given in [With more time](#10-with-more-time) rather than the work being quietly omitted.

## 6. Analysis queries and findings

All queries live in `analyses/`, dbt's native location for SQL that should compile with `ref()` resolution but not materialise as a table. They are numbered in four groups: data quality, completions, listen-through rate, and engagement.

### Data quality

**`01_data_quality_summary`** reconciles raw, deduplicated, valid and rejected event counts with a breakdown by rejection reason. See [Data quality findings](#4-data-quality-findings).

### Completions

A note on what "completed" counts. These analyses count `complete` **events**, not distinct listeners who completed an episode. A user-episode pair can carry more than one `complete`, and without session data there is no way to distinguish a genuine re-listen from a duplicate. Counting events is the honest reading of what the source records, but it is a weaker claim than the phrase "most completed episodes" suggests, and a stakeholder asking "how many people finished this episode" would want distinct listeners instead. That is a one-line change; the point is that the two questions are not the same and the column name should not blur them or make it ambiguous.

**`02_top_10_completed_episodes_last_7_days`**

The window is calculated from the data's own maximum event date rather than hardcoded, so it remains correct against different or growing data. `episode_id` is used as a secondary sort key to make ties deterministic; without it, which episode occupies the final position changed between runs.

Episode 19 leads with 8 completions. The tie-breaking matters more than it first appears: positions 5 through 10 are all tied at 4 completions, so which six episodes occupy those places is arbitrary beyond the sort key. With the dataset, it must be noted that a seven-day window produces counts too small to rank confidently so a bigger window is recommended or looking at the all-time view.

**`03_best_performing_episodes_alltime`**

Episode 84 leads with 204 completions. Notably, Episode 19, which topped the seven-day window, ranks only seventh all-time with 137 completions. The two windows disagree, which is consistent with the small-sample caveat above rather than evidence of a recent surge.

**`04_best_performing_podcasts_alltime`**

Podcasts are ranked by average completions per episode, not total. Catalogues range from 3 to 13 episodes, so a total-based ranking would largely reward catalogue size.

The podcast with the highest raw total (615 completions across 13 episodes) ranks thirteenth by average, at 47.3 completions per episode. The leader by average manages 97.0 completions per episode from a catalogue of just three. Ranking by total would have inverted the picture entirely.

The reverse bias is worth naming too: ranking by average rewards small catalogues, since a single strong episode is not diluted across a large back catalogue. Neither measure is fair on its own, and a production version would likely apply a minimum-episode threshold before ranking.

### Listen-through rate

**`05_avg_listen_through_rate_by_country`**

Reads `listen_through_rate` from the fact table, filtered to listen events (`pause`, `seek` and `download` have no duration and so no rate).

Rates sit in a tight band across all eight countries, roughly **0.745 to 0.768**. No country stands out as materially more or less engaged. All values fall below 1.0, confirming the capping treatment behaves as intended.

**`06_avg_ltr_by_podcast`** and **`07_avg_ltr_by_episode_length_bucket`**

Episode length shows a clean, monotonic relationship with completion:

| Bucket | Average listen-through rate |
|---|---|
| Short | 0.95 |
| Medium | 0.83 |
| Long | 0.61 |

Shorter content is more fully consumed.

### Engagement

**`08_users_3plus_episodes_in_a_day`**

72 users of 400. As set out above, this figure is highly sensitive to the definition of "listened" and should be read alongside it.

**`09_single_vs_multi_podcast_listeners`** and **`10_top_podcast_share_per_user`**

A binary single-podcast versus multi-podcast split finds almost no signal: 395 of 400 users engaged with multiple podcasts, averaging 26.7 distinct episodes each, against four single-podcast listeners and one user with no listens at all. Three of those four have very little activity, at three to seven listen events each, so they look less like loyal listeners than like users who never had the chance to branch out. The fourth does not fit that reading at all: 40 listen events across nine episodes, every one of them on a single show. That is exactly the loyal listener the analysis is looking for, and an average over four rows hid it. Worth stating plainly, because summarising a four-row result with a mean was the wrong move and the underlying rows say something the summary did not. Across 200 episodes and 30 podcasts, touching more than one podcast is close to inevitable for anyone active, so the measure cannot discriminate.

That single no-listen user is worth a note, because it only appears at all thanks to a `nullif` in `mart_user_engagement`. SQL's `count()` returns zero, not null, for a user who has events but none that qualify as listens, so without it that user would be silently bucketed as multi-podcast having listened to nothing. It is a one-row problem in this dataset and would be a much larger one in production.

Refining it to a continuous measure, the share of a user's listens going to their single most-listened podcast, does show real variation: an average of 0.40, ranging from 0.07 to 1.00. That range is the useful part. Some users spread their listening thinly across the catalogue while others concentrate almost entirely on one show.

## 7. Testing

`dbt build` runs 26 tests, all passing.

**Generic tests** cover uniqueness and non-nullity on every natural and surrogate key, referential integrity from `fct_listening_events` to both dimensions, and accepted values on `event_type` and `episode_length_bucket` (so a typo or unexpected new category fails loudly rather than appearing silently as an unrecognised group in an analysis).

**Five singular tests** in `tests/` assert business logic specific to this project:

| Test | Asserts |
|---|---|
| `assert_capped_duration_never_exceeds_episode_length` | The capping logic was applied correctly |
| `assert_rejected_rows_have_a_reason` | No row is quarantined without at least one flag set |
| `assert_no_event_id_in_both_fact_and_rejected` | Every event is classified as exactly one or the other |
| `assert_valid_plus_rejected_equals_total_staged` | Valid and rejected counts reconcile to the staged total |
| `assert_capped_duration_null_for_non_listen_events` | The capped duration is populated exactly when the event is a listen |

Two of these are regression guards rather than genuine checks. Given how `is_rejected` is derived in staging, a quarantined row necessarily has a reason, and the fact and quarantine tables necessarily cannot overlap. They earn their place by failing if that derivation is ever changed, not because the current code could plausibly get them wrong, and presenting them as evidence of business-logic coverage would overstate what they do.

The other two test properties not guaranteed by construction. The reconciliation test proves no row is silently lost or duplicated between staging and the fact/rejected split. The null-guard test exists because `least()` ignores nulls in DuckDB: `least(null, 1800)` returns 1800, not null, so without an explicit guard every pause, seek and download row would claim a full-episode listen. The existing capping test cannot catch that, since an episode's length does not exceed itself.

It reconciles from the staged count rather than the raw seed count deliberately. Deduplication happens in staging by design, so the raw total is legitimately higher, and that difference is reported in `01_data_quality_summary` rather than hidden inside a test. When deduplication was first introduced, this test failed immediately, which is exactly the behaviour intended: a change that quietly dropped rows was caught rather than absorbed.

Generic tests are applied to keys and constrained-value columns only, including a compound-key uniqueness test on `int_user_daily_activity(user_id, event_date)`, but not to every column.

## 8. Orchestration

**Note on experience:** I have designed pipelines and handled scheduling in other tools, but have not used Airflow hands-on. What follows is a considered design rather than a description of something I have operated, and standing up an actual DAG would be an early priority.

A daily DAG running overnight, so squads have current figures at the start of the working day:

```
extract / load  ->  dbt build  ->  alert on failure
```

**Start simple.** `dbt build` as a single task (running models and tests together, halting the run if a test fails) is where most teams begin and is appropriate here. dbt already understands the dependency graph between models; Airflow does not need to re-solve it, only to trigger the run.

**Add granularity when it earns its place.** The limitation of a single task is that a failure surfaces as "the dbt step failed" rather than naming the model. [Astronomer Cosmos](https://github.com/astronomer/astronomer-cosmos) parses the dbt manifest and generates one Airflow task per model, giving per-model visibility in the Airflow UI. Worth adopting once the project is large enough that the setup cost is justified.

**Alerting should be graded, not binary.** Roughly 3% of events currently fail validation, and that baseline is expected rather than alarming. A useful alerting strategy distinguishes between them:

- `severity: warn` when the rejection rate drifts meaningfully above its established baseline, indicating something has changed upstream
- `severity: error` for genuine integrity failures, such as a referential integrity break or a reconciliation mismatch

Because rejection reasons are independent flags, a rate spike can be diagnosed by grouping on reason rather than treated as one undifferentiated number. A jump concentrated in `is_missing_user_id` points somewhere quite different from one spread evenly across all six.

Alerting to Slack or email on test failure matters more than the DAG structure itself. Silent failure is the outcome to design against.

**Idempotency.** Reruns after a failure, and backfills of missed days, must not produce duplicates. With an incremental fact table this means a `unique_key` (the existing `event_id` serves directly) so that a repeated row updates rather than duplicates, with `--full-refresh` available as a controlled reset.

**Incremental models.** `fct_listening_events` is built as a standard view here, because the seed is fully reloaded on every run and there is no meaningful notion of new data to demonstrate against. In production, with an append-only event stream, it would be incremental: filtered on `event_datetime` against the maximum already loaded, with `unique_key` set to `event_id`.

## 9. Extensibility

A reasonable test of this model is what happens when a new product feature ships and its impact needs measuring.

**If the feature fits the existing event shape**, no schema change is required at all. For example: `download` was added to the event stream after the model was built, and the only change required anywhere in the project was extending the `accepted_values` test on `event_type`. The event flowed through staging, was validated by the same checks, and landed in `fct_listening_events` at the same grain without any model being touched. This is the payoff of modelling the fact table generically around "an interaction event" rather than hardcoding it to a fixed set of types.

The one genuine decision it forced was semantic rather than structural: does a download count as a listen? It does not, for the reasons given under "Defining listened" above. That question is the useful part, and the model surfaced it rather than absorbing the new type silently.

**If the feature introduces new attributes** (playback speed, a feature flag indicating exposure), that is an additional column in staging for something low-cardinality, or a companion table joined at the same grain for something more structured. Either is isolated to the staging and intermediate layers, leaving existing models untouched.

**Measuring impact properly needs more than a date cut.** A before-and-after comparison cannot separate the feature's effect from any other trend occurring at the same time. Meaningful impact analysis requires an exposed-versus-control split, which in turn requires an `experiment_id` or feature flag dimension captured at the event level from the outset. That is a requirement to raise with the product team before a feature ships, not something that can be reconstructed afterwards.

**Handling new data quality checks.** If a new class of error appears upstream, adding a row-level check means adding one boolean flag in `stg_event_logs`. Existing flags and queries are unaffected, and `rejection_reason_summary` is derived from whatever flags exist, so it picks the new one up automatically. `assert_rejected_rows_have_a_reason` is worth being precise about here, because it is easy to oversell. `is_rejected` is a disjunction of the six flags, so a row cannot be rejected without one of them firing. The test cannot detect a new upstream error class.

Checks that compare rows against each other are the exception, as deduplication demonstrated. Those need their own mechanism rather than another flag.

Under a full refresh, adding a check is straightforward, as it simply applies to all history on the next run. Under an incremental model it becomes a real decision. Backfilling is correct where the check is retrospectively computable from retained columns. Where it is not, leaving historical rows null is more honest than marking them false, since "not checked" and "checked and passed" are genuinely different statements. The cleaner mechanism is a `rejection_ruleset_version` column recording which set of checks was applied to each row, which makes coverage explicit rather than something inferred from nulls.

## 10. With more time

For example, data does not currently support it and/or not yet built:

- **New versus returning listeners per episode.** 
- **Whether seeking or pausing predicts abandonment**
- **Engagement concentration among the heaviest users**
- **Cohort retention.**

**Data that would need to exist**

- **Session identifiers**, the single most valuable addition. They would unlock true total listening time, within-episode drop-off, and genuine sequencing of user behaviour.
- **A source-emitted event identifier**, so identity does not have to be derived from row content. This would remove the deduplication ambiguity described above entirely.
- **Geographic granularity beyond country**, allowing regional rollups. A country-to-region lookup would be a small seed table.
- **Podcast metadata as a source.** There is no podcast table, only `podcast_id` on episodes. A derived `dim_podcasts` (distinct podcasts with episode count and release date range) is trivial to build, but ideally podcast attributes such as title, genre and host would come from a system that owns them rather than being reverse-engineered.

**Engineering hardening**

- **Model contracts** on `fct_listening_events` to enforce column types and constraints at build time
- **CI**, running `dbt build` on every pull request
- **Snapshots**, to capture slowly changing dimensions. Nothing changes in this static dataset, but if a user's country or an episode's metadata changed in production, the model currently has no mechanism to track the historical state
- **Exposures**, documenting known downstream consumers of the marts once they exist

## 11. Known limitations

- **Listen-through rate depends on a capping decision**
- **"Listened" is a defined term, not a given one.**
- **Deduplication is lossy in principle.**
- **Episode length bucket thresholds are provisional and require sign-off in reality**
- **Total listening time cannot be established from this data.**
- **Seven-day rankings rest on very small counts.**
- **A fifth of valid events predate their episode's release date**
- **The findings recover patterns designed into the generator e.g. concentration findings/loyalty**
- **"Completed" means completion events, not distinct listeners.**

The judgement calls are mine, and they are documented throughout rather than

a listen, why invalid rows are quarantined rather than dropped, why podcasts
